## 사례 1. SSH/HTTP 접속 시 `Connection timed out`

| 항목 | 내용 |
|---|---|
| 증상 | EC2 생성 후 `ssh -i <키>.pem ubuntu@13.125.200.239`가 `Connection timed out`. 포트 80(`curl -m 10 http://13.125.200.239`)도 동일하게 타임아웃 |
| 원인 가설 | ① 보안 그룹 22번 소스 IP가 현재 공인 IP와 불일치 ② 인스턴스가 다른 VPC/서브넷/보안 그룹에 생성됨 ③ 라우팅 테이블이 서브넷에 연결되지 않음 ④ 사용 중인 네트워크가 22번 포트를 차단 ⑤ 네트워크 ACL 차단 |
| 검증 방법 | ① `curl -4 ifconfig.me` 결과(`121.135.x.x`)와 SG 22번 소스(`121.135.x.x/32`) 대조 → **일치, 배제**<br>② 인스턴스 상세에서 VPC(`Codyssey-VPC`), 서브넷(`Codyssey-public-subnet`), 보안 그룹(`Codyssey-web-sg`), 퍼블릭 IPv4(`13.125.200.239`) 확인 → **정상, 배제**<br>④ 22번뿐 아니라 80번도 타임아웃 → 22번만 막는 네트워크 문제로 보기 어려움<br>③ 라우팅 테이블 `Codyssey-public-rt` 상세 확인 → `0.0.0.0/0 → igw-09189f3a55fa268b7` 경로는 있으나 **"명시적 서브넷 연결"이 비어 있음 → 원인 확정** |
| 조치 | `Codyssey-public-rt` → 서브넷 연결 편집 → `Codyssey-public-subnet` 연결 저장 |
| 결과 | 같은 `curl` 요청이 `Connection timed out`에서 `Connection refused`로 변경. 타임아웃은 패킷이 중간에서 사라진 것이고, 거절은 패킷이 서버까지 도달해 80번을 듣는 프로세스가 없어 거부된 것이라 경로가 복구된 것으로 판단. 이후 SSH 접속, Nginx 설치, 외부 접속까지 정상 동작 |
| 재발 방지 | 라우팅 테이블에 경로를 추가한 뒤에는 **"명시적 서브넷 연결" 칸에 서브넷이 표시되는지**까지 확인한다. 배포 전 체크리스트에 `IGW Attached`, `0.0.0.0/0 → IGW`, `서브넷 연결`, `퍼블릭 IP 부여`, `SG 규칙`을 넣어 인스턴스 생성 전에 점검한다 |

### 배운 점
- 서브넷은 라우팅 테이블을 명시적으로 연결하지 않으면 VPC의 기본(main) 라우팅 테이블을 따르고, 이 테이블에는 `local` 경로만 있어 인터넷으로 나갈 수 없다.
- `timed out`(응답 없음)과 `refused`(즉시 거절)를 구분하면 문제 위치를 좁힐 수 있다. 타임아웃은 네트워크 경로나 방화벽, 거절은 서버까지 도달했으나 해당 포트를 듣는 프로세스가 없는 경우다.

## 사례 2. IAM 사용자 콘솔 로그인 실패 (`Authentication failed`)

| 항목 | 내용 |
|---|---|
| 증상 | IAM 사용자 로그인 화면에서 "인증 정보가 정확하지 않습니다" 오류 |
| 원인 가설 | ① "Account ID or alias" 칸의 값이 잘못됨 ② IAM 사용자명 불일치 ③ 비밀번호 오류 |
| 검증 방법 | 입력값을 항목별로 대조. 계정 ID/별칭 칸에 콘솔 우측 상단의 **계정 이름**(`junhnno`)을 입력했음을 확인. 계정 이름은 로그인용 식별자가 아니며, 별칭(alias)은 설정한 적이 없음 |
| 조치 | 계정 ID/별칭 칸을 12자리 **계정 ID**로 교체하고 재시도 |
| 결과 | 로그인 성공 |
| 재발 방지 | 계정 ID, 계정 이름, 계정 별칭을 구분한다. 로그인 URL(`https://<계정ID>.signin.aws.amazon.com/console`)을 저장해 두거나 IAM 대시보드에서 계정 별칭을 설정한다 |

### 배운 점
- 로그인 오류 문구는 어느 입력칸이 틀렸는지 알려주지 않으므로(계정 정보 노출 방지로 추정), 입력값을 하나씩 대조하며 원인을 좁혀야 한다.

## 참고: 최소권한 관련 한계

IAM 권한은 사용자 그룹 `lab-ec2-vpc`에 AWS 관리형 정책 `AmazonEC2FullAccess` 하나만 연결해 구성했다. 이 정책은 EC2/VPC/보안 그룹 작업을 수행하기에 충분했고 별도의 권한 오류는 발생하지 않았다. 다만 관리형 정책이라 과제에 필요한 동작과 서울 리전으로 좁힌 고객 관리형 정책보다 범위가 넓다. 실무에서는 필요한 동작과 리전으로 제한한 정책을 사용한다.
